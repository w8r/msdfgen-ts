msdfgen-ts vs webgl-sdf-generator, at equal memory

Both libraries turn TrueType outlines into distance-field atlases at runtime: msdfgen-ts builds a three-channel MSDF on the CPU, webgl-sdf-generator (the generator behind troika-three-text) builds a one-channel SDF on the GPU. Here both get the same outlines, the same atlas layout and the same texture memory, and the rendered glyphs are compared against an exact rasterization of the outline.

  • At normal sizes, a tie.Up to 2× the atlas resolution, PT Serif shows at most {{pt.d80.msdf}}% wrong pixels for either method. Mean edge error is about 0.02 px for both; the SDF is slightly lower at 1× ({{pt.e40.rgb}} vs {{pt.e40.msdf}} px) because it has more texels.
  • Magnified, MSDF keeps its corners.PT Serif at 8× (320 px/em): {{pt.d320.msdf}}% wrong pixels for MSDF against {{pt.d320.rgb}}% and {{pt.d320.rgba}}% for the SDF. The SDF needs {{pt.iso320.rgb}}× MSDF's bytes to catch up ({{pt.iso320.rgba}}× counting the RGBA8 texture msdfgen-ts uploads).
  • Overlapping contours erase that lead.Roboto at 8×: {{rb.d320.msdf}}% for MSDF against {{rb.d320.rgb}}% and {{rb.d320.rgba}}%. msdfgen, and so msdfgen-ts, cuts seams where contours overlap, which also costs a few pixels at 1×.
  • webgl-sdf-generator is far faster to build.On the GPU it writes the 160-glyph equal-memory atlas in {{pt.t.into}} ms; msdfgen-ts takes {{pt.t.ours}} ms on the CPU, about {{pt.t.speedup}}× longer.

Overlapping contours: MSDF cuts a seam

Roboto draws the 8 as two overlapping loops. msdfgen's channel logic fails where they cross and cuts a seam through the waist. The C++ msdfgen reference does the same (its bitmap for this glyph is in test/golden/roboto/U0038_48px), so this is inherited behavior, not a porting bug. Upstream avoids it by merging overlaps with Skia first, which this port leaves out. The single-channel SDFs are unaffected.

Wrong pixels
Pixels whose coverage differs from the truth by more than 0.5, as a percentage of the pixels the true edge passes through. At extreme magnification it can pass 100%.
Edge error
Sum of |coverage − truth| divided by the outline's length in pixels: roughly the average distance between the drawn edge and the true edge, in screen pixels.
Display sizes
Device pixels per em. 40 px/em is the MSDF atlas's resolution, so 320 px/em is 8× magnification for the MSDF and about 4.6× for the RGB8-matched SDF.

The atlases

The three equal-budget atlases as they are stored, drawn at one shared texel scale, so their areas compare directly. The MSDF packs three distance channels into each texel; the SDF spends the same bytes on about three or four times as many single-channel texels.

How the comparison was made

Held equal

  • Outlines. Both generators receive the same em-normalized outline from the msdfgen-ts TrueType parser, passed to webgl-sdf-generator as an SVG path (M, L, Q, Z). The ground truth uses that outline too.
  • Atlas layout. Every glyph is cropped to its ink bounds plus the same padding in em, as msdfgen-ts's Atlas does, and packed with potpack. Texel centres sit at the same positions in both.
  • Distance range. 0.1 em in total for both: pxrange 4 at 40 px/em for the MSDF, maxDistance 0.05 em with exponent 1 for webgl-sdf-generator. With those settings its bytes encode distance exactly as msdfgen does (d / range + 0.5). An equal range in em means both support the same smallest text size and leave the same room for outlines and glows.
  • Rendering. One function draws both: bilinear filtering of the 8-bit texels, clamped to the glyph's cell, then clamp(screenPxRange × (d − 0.5) + 0.5, 0, 1). The only difference is d = median(r, g, b) for MSDF and d = r for the SDF.
  • Memory. The SDF's resolution was raised in 0.25 px/em steps until its packed atlas was as large as the MSDF atlas. Two accountings: equal bytes of distance data (MSDF at 3 bytes per texel), giving {{pt.rgb.px}} px/em ({{pt.rgb.atlas}} = {{pt.rgb.kb}}); and equal bytes against the 4-byte RGBA8 texture msdfgen-ts's Atlas uploads today, since WebGPU has no RGB8 format, giving {{pt.rgba.px}} px/em ({{pt.rgba.atlas}}). A one-channel SDF costs one byte per texel, whether as R8 or packed four glyphs per RGBA texel as troika does. The “same texel size” option in the viewer gives the SDF only a third of the memory, for reference.

Measured

  • Glyphs. {{glyphs}} per font, printable ASCII plus Cyrillic А–я, Ё and ё, from PT Serif Regular (serifs, sharp corners) and Roboto (sans-serif, overlapping contours), the repository's test fonts.
  • Ground truth. Exact area coverage of the outline under the nonzero fill rule: 64 sub-scanlines per pixel row with analytic horizontal coverage, curves flattened to within 0.01 px. It shares no code with either generator.
  • Renders. Each glyph alone at 20, 40, 80, 160, 320 and 640 px/em, at a fixed sub-pixel offset (0.37, 0.61 px) so straight stems do not land exactly on pixel boundaries.

Fairness checks

  • The JavaScript path is the GPU path. The numbers use webgl-sdf-generator's JavaScript implementation, which needs no GPU. Running its WebGL implementation in headless Chromium on {{renderer}} produced identical bytes, apart from {{pt.parity.diff}} of {{pt.parity.total}} (PT Serif) and {{rb.parity.diff}} of {{rb.parity.total}} (Roboto) that were off by at most {{pt.parity.max}}, from float32 versus float64 rounding.
  • Curve flattening costs nothing visible. webgl-sdf-generator replaces each curve with 15 straight segments. msdfgen's exact single-channel SDF at the same budget scores the same on PT Serif ({{pt.d320.rgb}}% and {{pt.d320.exact}}% wrong pixels at 320 px/em). On Roboto the exact SDF does better because it handles overlapping contours.
  • Encoding. troika-three-text uses exponent 9 with a range as large as the glyph cell, decoded after filtering. A one-off check at the RGB8 budget gave the same wrong-pixel rate as exponent 1 to within 0.05 points (PT Serif at 320 px/em: 2.52% for both) and about 30% more edge error, so the linear encoding used here does not handicap the SDF.
  • Limits. One MSDF setting (40 px/em, pxrange 4, the library default). Filtering is exact bilinear on the CPU; GPU filtering of 8-bit textures is coarser, equally for both. No mipmaps, so minification is only tested down to 0.5×.

Side findings

  • msdfgen-ts inherits msdfgen's overlap artifacts. Roboto's 8, Ф, q and 4 show seams or notches. The repository's golden bitmap from the C++ reference for Roboto 8 has the same seam. Upstream msdfgen fixes this by resolving overlaps with Skia before generating, which this port leaves out by design.
  • webgl-sdf-generator's WebGL1 path breaks on non-power-of-two sizes. By default it creates a WebGL1 context, and its internal textures keep the default REPEAT wrap mode. Under WebGL1 a non-power-of-two texture with REPEAT is incomplete, so every texel comes back as 255, with no error and no fallback. Its isSupported() check renders a 4×4 test and misses this. troika avoids it with fixed 64×64 cells. Passing a WebGL2 context, as this comparison does, fixes it.
  • webgl-sdf-generator draws lines inside overlapping contours. It takes the nearest distance over every segment, including edges buried inside the fill, as the Roboto Б above shows.
